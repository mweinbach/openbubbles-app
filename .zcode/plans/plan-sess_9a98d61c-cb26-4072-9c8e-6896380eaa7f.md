# Transition OpenBubbles to Rust + Kotlin (no Dart)

## Decisions used (recommended defaults — veto any)
1. **UI: Compose Multiplatform** — one Kotlin UI for Android *and* Windows; Rust core via the existing UniFFI bridge on both.
2. **Logic split: Kotlin** — Rust keeps the protocol core (as today); message handling, ObjectBox persistence, ViewModels go to Kotlin (nearly mechanical port from the Dart services).
3. **v1 milestone: Messaging MVP** — login, chat list, chat view, send/receive + attachments, notifications. Long tail (FindMy, FaceTime UI, posters, send effects, theme studio) in later milestones.
4. **Theming: one skin (Material 3 + dynamic color) for v1.**

## Why this is tractable
- The hard part — 35.4k lines of Apple protocol Rust (`rustpush/`) — is untouched.
- ~17.4k lines of Kotlin already talk to Rust directly (APNService push daemon, credentials/autofill, FaceTime call activity, notification builders) and carry over as-is.
- GetX usage is shallow (Rx as change-notifier) → maps ~1:1 to `StateFlow`/ViewModel. DI is GetIt → Koin/Hilt.
- ObjectBox schema is flat (9 entities) and **ObjectBox-Kotlin runs on desktop JVM too** — one persistence layer for both platforms.

## Target architecture
```
openbubbles-app/
├── rust/               # existing cdylib — EXPAND UniFFI surface (M0)
├── rustpush/           # submodule — unchanged
├── shared/             # NEW KMP module (commonMain): Compose UI, ViewModels,
│                       #   ObjectBox-Kotlin entities+repos, UniFFI API consumer
├── app-native/         # NEW Android app module: Compose + existing Kotlin services
│                       #   (APNService, credentials, FaceTime, notifications moved in)
├── desktopApp/         # NEW Compose Desktop main (Windows; runs the poll loop in Kotlin)
├── android/ + lib/     # Flutter app stays INTACT + shippable until M4 cutover
└── (deleted at M4: lib/, rust_builder FRB glue, Flutter deps, 82 MB committed jniLibs)
```

## Milestones (each ends buildable + testable)

**M0 — Foundations**
- Gradle: add `:shared` (KMP android+jvm) and `:app-native` (Compose) modules; Rust built via cargokit into `app-native`; separate applicationId suffix during dev.
- **UniFFI expansion** (the prerequisite — today only ~21 of ~208 Rust fns are Kotlin-reachable): expose send path (`new_msg`/`send`/`validate_targets`), attachments (upload/download with progress callbacks), login/2FA/phone auth, registration, queue consumption (`read_queued_message`/`mark_queue_attempt`/`complete_msg`), typing/markRead/rename, CloudKit sync entry points; wrapper `Record` types for rustpush structs. Add a gradle check so bindings can't drift (today they're manually generated + committed).
- **ObjectBox-Kotlin with UID parity**: port entity/property UIDs from `objectbox-model.json` into Kotlin `@Uid` annotations so the native app opens the *same store files* the Flutter app wrote — user history survives the eventual in-place update. Fallback: the app's existing backup/restore feature.
- CI: add native build job (cargo + `:app-native` assemble + desktop distZip).

**M1 — Messaging MVP (first usable native build)**
- Setup/login flow (Apple ID + 2FA + phone; reuse native `AuthCodeActivity` patterns).
- Conversation list (M3 dynamic color, search, pinned, swipe actions).
- Conversation view: text messages, grouping, sent/delivered/read/failed states, typing indicator, image attachments, send field, tapbacks (render + send).
- Kotlin message intake: port `handleMsg`/`reflectMessageDyn`/`IncomingMessageHandler` (~2k lines of logic) replacing the Dart queue; APNService hands pushes to Kotlin directly (pointer scheme already exists).
- Notifications: existing Kotlin builders re-wired from method-channel to direct data source.

**M2 — Daily-driver parity**
- Full attachments (video/audio/docs/live photo, MMCS), edits/unsend, groups, contact sync + avatars, chat details/media gallery, core settings panels, backup/restore, CloudKit sync (isolates → Kotlin workers), SMS/MMS (native Kotlin — telephony_plus was a Flutter plugin), share intents, quick reply, Android bubbles, app shortcuts.

**M3 — Long tail**
- Find My, FaceTime UI (mostly native already), contact posters, passwords UI (native exists), StatusKit/zen, shared albums, desktop shell (tray, window effects, spellcheck), Windows packaging (MSIX/Inno), send effects (port the ~3.1k lines of particle math), optional iOS skin + theme studio.

**M4 — Cutover**
- `applicationId` + versionCode continuity → in-place update preserves data; migration tested against a real Flutter-app DB. Swap default launcher, **delete `lib/`, FRB glue, Flutter deps, and the 82 MB committed `jniLibs` .so files** (built from source now), rewrite CI/README.

## Risks / honesty
- ~123k lines of handwritten Dart get replaced. M0+M1 alone is a multi-session effort; the full ladder is weeks. Each milestone ships something runnable, and the Flutter app stays the daily driver until M4.
- Hardest recreations: conversation-view orchestration (24k lines Dart, we rebuild simplified), attributedBody mention rendering, adaptive theming (deferred), UniFFI record wrappers for rustpush types.
- Two dev apps coexist until cutover; DB continuity is designed-in via UID parity, with backup/restore as the safety net.

## First steps on approval
1. Gradle restructure (`:shared`, `:app-native`) with a hello-Compose screen building against the existing Rust `.so`.
2. UniFFI expansion batch 1 (state/queue/send) + regenerated bindings + drift-check task.
3. ObjectBox-Kotlin entities with UID parity + a test opening a copy of a real store.
